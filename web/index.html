Blob storage · Blob Lab

Big bytes never touch your servers.

The whole pattern in one line: metadata in a DB, bytes in object storage, presigned URLs both ways. The interesting engineering is durability economics — how eleven nines is manufactured (failure domains + repair speed, not copies), what erasure coding buys over replication, and why the surprise line on the bill is always egress.

Presigned URLs — pointers, not bytes

Proxying uploads through your API turns it into a file server. Instead the app server signs a short-lived capability URL (HMAC over method+key+expiry); the client talks to the object store directly. The app only ever writes a ~200-byte pointer row.

The proof: proxied, 50 × 2 GB in-and-out = ~400 GB in flight through your fleet — your API is now a file proxy. Presigned, the same uploads move 0 bytes through you; the store verifies the signature and expiry itself (a tampered key or a 61-second-old 60s URL is DENIED). Commit order matters: blob first, then metadata — a crash in between leaves an invisible orphan the GC sweep reclaims, not a user-visible dangling pointer.

Multipart upload — resume, don't restart

A 5 GB single PUT that dies at 80% restarts from byte zero. Multipart splits it into parts (each with an ETag), so a failure costs one part; ListParts tells the resuming client what survived, and Complete — the manifest commit — is the atomic point where parts become an object.

Eleven nines — manufactured, not bought

Copies alone don't give durability. Data is lost only when every copy dies before repair completes — so durability is a race between the failure rate and the repair rate, multiplied by the independence of failure domains.

The proof: one copy loses ≈ AFR = 2%/yr (1.7 nines — losing 1 in 50 objects is not a product). Three copies with a 30-day repair window: 1.5e-7. Shrink repair to 3 hours and the same three copies hit 2.8e-12 — eleven-plus nines — repair speed did that, not more copies. Put the three copies in one rack and correlation collapses it back toward the AFR: independence is the third factor.

Erasure coding vs 3× replication

Split a blob into k=4 data + m=2 parity shards: lose any two and reconstruct exactly — the same 2-loss tolerance as three full copies at half the bytes. The price: repairs read k shards and degraded reads must reconstruct.

The object lives as 6 shards (4 data + 2 parity).

The proof: all 15 possible 2-shard losses reconstruct byte-identically; a third loss is unrecoverable (m=2 tolerates exactly 2). Same protection, half the storage bill — which is why cold tiers are erasure-coded while hot tiers stay replicated: replication's cheap reads and 1-shard repairs are worth the bytes when the data is busy.

Content-addressable storage — the key is the hash

Key every blob by sha256(content): identical content → identical address → stored once. Every read self-verifies (a flipped bit changes the hash), and "editing" writes a new address — immutability by construction, at the price of refcounted GC.

Deletion is a state machine

Synchronously deleting from every replica, CDN, and backup is slow and partial-failure-prone (one timeout = a half-deleted blob). The real pipeline: tombstone (one atomic row, user sees 404 in ~2 ms) → grace window (undelete works) → async GC → compaction reclaims the container space.

The proof: the tombstone is one ~2 ms metadata write — the user's 404 is immediate while disk usage is unchanged. Inside the 7-day grace window undelete is free. The day-10 GC frees tombstoned bytes and compaction rewrites the 71%-dead container from 40 MB to 11 MB. Lifecycle policies (age → cold tier → expire) are the same machinery pointed at the bill.

Your key naming is your load distribution

Object stores partition by key prefix and rate-limit each partition (~3,500 PUT/s). Timestamp-led keys (logs/2026-08-17/…) funnel every write to one partition; a hashed prefix spreads the same traffic flat.

The proof: timestamp keys → one partition carries everything: 3,500 served, 8,500 × 503 (71% rejected). Hash-prefixed → 16 partitions × ~750 req each, zero throttling. A hot object is different: replicate it, or front it with the CDN (next lesson).

CDN — cache the blob, version the URL, watch egress

Put edge PoPs in front of the store: reads become "one miss per PoP", latency flattens worldwide, and origin egress collapses. Invalidate by versioned/content-hash URLs (immutable forever), not purges; sign private URLs so the edge itself rejects tampering.

The proof: the CDN takes ap-south from 205 ms to 16.5 ms at a 99.5% hit ratio, collapsing origin egress 293× (88.6 GB → 0.30 GB). On a deploy, purge-by-path leaves a window of stale reads while the purge propagates; versioned URLs serve zero stale reads and need zero purges — the old name just ages out. At 1 PB/month the bill: no CDN $94k; CDN at 90% edge-hit $51k — and a cold CDN (0% hit) is worse than none, because you pay both meters.
